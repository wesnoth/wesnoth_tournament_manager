# Wiki and Help Implementation

This document describes the stable architecture of the integrated help system. The source code is the authoritative reference for endpoint behavior, validation rules, and implementation details.

## Public help

Authenticated and anonymous users can browse published articles through `/help` and `/help/:slug`. The frontend loads the article navigation and the selected article from the public wiki API. Articles are stored as one database row per slug, with a JSON `translations` object containing the title and Markdown content for each language.

The Help/Wiki article collection is the canonical user-facing documentation for the application. The legacy `User_Manual_en.md` document has been retired; new workflows and product guidance belong in published Wiki articles, with localized translations where appropriate.

The `/help` landing page always opens the `getting-started` article. The global Help control uses an explicit route-to-article map for stable public sections and falls back to `getting-started` for private, administrative, or otherwise undocumented routes. The documented audit page maps `/admin/audit` to the `admin-audit` article. A missing contextual article is also redirected to that landing article, so broad route prefixes such as `/admin` cannot accidentally select an unrelated article.

When the requested language is unavailable, the backend returns the English translation. The response includes the language actually returned so the UI does not claim to display a translation that does not exist.

Markdown is rendered in the browser and sanitized before it is inserted into the page. Wiki images are served through `/api/public/wiki/images/:filename`; image filenames are generated by the backend and are never treated as arbitrary filesystem paths.

Rendered links receive safe `rel` attributes, and public image serving accepts only generated-looking image filenames and supported image extensions. The same renderer is used for public articles and administrative previews, so sanitization and formatting behavior remain aligned across both surfaces.

The shared frontend renderer in `frontend/src/utils/wikiMarkdown.ts` is used by the public viewer, the administrative editor preview, tournament description/rules previews, tournament detail pages, and rule-template previews. These surfaces therefore share the same Markdown features, sanitization policy, image URL handling, and visual formatting.

## Administrative wiki management

Moderators and administrators can manage articles at `/admin/wiki`:

- create and edit multilingual Markdown articles;
- publish or keep articles as drafts;
- upload images for use in article content;
- inspect image usage and remove unused images;
- detect and clean files left on disk without database metadata;
- export an article and its referenced images as a ZIP package; and
- import a ZIP package after explicit overwrite confirmation.

The backend authorization middleware protects every administrative endpoint. The authenticated user ID is used for article and image ownership; clients do not provide authoritative author identity.

Image uploads are held in memory only for the request and are limited to 5 MiB. MIME types are restricted to JPEG, PNG, GIF, and WebP. Article updates require a non-empty English title and body, and ZIP metadata is validated before any imported image is written.

## Image lifecycle

An uploaded image has a filesystem file, a `wiki_images` metadata row, and zero or more rows in `wiki_article_images`. Saving or importing an article rebuilds its image links from the Markdown content. Deleting an article removes its image links but retains the registered images for possible reuse. The image library reports their live article usage count and allows moderators or administrators to delete all registered images with zero uses after confirmation. An image that is still referenced cannot be deleted.

Files present on disk without corresponding database metadata are reported separately as unregistered files. They indicate a storage consistency issue rather than ordinary unused library content and can be removed through their own explicit cleanup action.

## Import and export

Exports contain `article-metadata.json` and an `images/` directory. Markdown image URLs are converted to relative paths in the package and restored to public API URLs during import. Import validation requires a valid slug, at least one valid translation, and a complete English translation. Overwriting an existing article requires an explicit confirmation from the administrative UI and replaces its translation and image-link set.

## Persistence model

The current model uses UUID `char(36)` article IDs, a globally unique slug, JSON translations, and an image junction table keyed by `(article_id, wiki_image_id)`. `backend/src/config/schema.sql`, the active migration history, and the deployed database must remain aligned before any schema migration is applied. The detailed SQL and runtime behavior belong in the schema and source code, not in this overview.

The original experimental wiki migrations are retained under `backend/migrations/deprecated/` for historical reference and are not part of the active migration sequence. The active corrective migration only aligns the existing image junction foreign key with the UUID article ID; the existing ZIP packages are the recovery path for rebuilding article-image links.
